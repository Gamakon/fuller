Title: Metal compute kernel never completes (status stays "scheduled") although every loop has a trip bound of at most 32; the pipeline builds in 33 ms

Where it hangs: in the DISPATCH on the GPU, not in compilation. makeLibrary and makeComputePipelineState return in 33 ms; the command
buffer is committed and its status stays 3 (scheduled) for the whole 8 s wait (the same with 120 s). Killing the process ends it.

Environment: macOS 26.6.2 (25G83), Apple M3 Max (40 GPU cores), Metal toolchain 32023.883 (metalfe), MTLCompileOptions.languageVersion = 2.4,
makeLibrary(source:) at run time. One threadgroup of 16 x 16 threads. Source generated by naga 30 (the WGSL compiler of wgpu 30) from a WGSL kernel.

Reproduce: swiftc -O run_msl.swift -o run_msl; ./run_msl naga_msl_reduced.metal 8
  prints "compile+pipeline 33 ms" then "HANG in dispatch after 8.0 s; status 3". Run it alone with a time limit: after the process is killed the
  GPU can stay busy for seconds.

What the kernel does (naga_msl_reduced.metal, function main_): an empty `while` loop that runs 32 times; one write of a float2 from a
determinant of a zero 4x4 matrix; a `while` loop that runs once (nx1_ = 1) whose body does one dynamic-lane store into a thread-local array of
float2 and then breaks. The program terminates after 33 loop iterations in all.

Evidence that the program is correct and the compiler/GPU is at fault:
 - Instrumenting the first loop (h_1[0] = k1_ each trip) shows k1_ holding 1292559263 (garbage) after the hang: the loop counter, a local variable
   that is only ever 0..32, is corrupted or uninitialised in the generated code. The statement after the first loop was never reached.
 - Replacing the condition ((_e428 / _e429.xyxy) - metal::sin(_e432)) >= _e435 (half4, all zeros) in the second loop by any of
   _e428 >= _e435, (_e428 / _e429.xyxy) >= _e435, (_e428 - metal::sin(_e432)) >= _e435, or bool4(false) makes the kernel finish in milliseconds
   (control_terminates.metal is one of them). The same hang with the half4 locals replaced by float4.
 - Removing the determinant statement, or the first loop, or reducing the second loop's body also makes it finish. Removing naga's `loop_bound`
   counters does not.
 - The two loops and the determinant are unrelated, so the hang depends on code that runs after the loop that is wrongly executed: a code
   generation fault, not a slow program.

Expected: the command buffer completes in under a millisecond. Actual: never completes.
