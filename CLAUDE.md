## Architecture (what's actually built)

- `src/expr.rs` — `Math` datatype (real-domain ops incl. `Protected*`) + `GUARD_RELATIONS` (is-positive/is-nonzero for guarded rewrites).
- `src/eval.rs` — real-domain evaluator over egglog `Term`s. `sqrt(neg)/log(≤0)/div0 → NaN`; protected ops match the engine's exact semantics (e.g. `ProtectedExp` = uncapped exp, +inf on overflow).
- `src/karva.rs` — karva (GEP chromosome) ↔ `Math` converter, keyed on `semantic_id` (NOT geppy name). Holds `master_pset()`.
- `src/ruleset/` — egglog rulesets: `identities` (algebra), `powers`, `distribute`, `rational`, `trig`.
- `src/extract.rs` — `denoise()`: saturate (algebra+powers only, bounded) → `extract_variants` → score on data → smallest within R² tolerance, else unchanged. The live mutation operator. Never raises.
- `src/physics.rs` — `generate()`: pure one-to-many physics-prior mutation GENERATOR (NO eval/score). Tags candidates `speculative` (caller must extrapolation-gate those).
- `src/snap.rs` — constant snapping (π/e/√2/G… within tol → symbol annotation; Math stays pure-numeric).
- `src/geneframe.rs` — the **nucleotable data model, owned here**: master `SymbolTable`, typed many-hot arity, kingdom = a query. The direction the symbol/pset layer migrates toward.
- **The geneframe holds two row kinds** (design 2026-10-09, `docs/PLAN_population_dag.md`): ordinary chromosomes and homeotic chromosomes (population-wide shared definitions with a stable row id, a root type, memoised row values and a referrer count). An href names a homeotic row by its stable id, never a position in the homeotic tail. Fold is a variation operator: it adds definitions, rewrites ordinary rows to reference them and re-sorts the homeotic tail by use; execution follows a separate level schedule (a definition after everything it references). The memoised top of the homeotic tail is the expressed frame. Determinism is a tested contract: values bit-identical with homeotic rows present or stripped.
- `src/population_dag.rs` — the population DAG on the host (plan task 3): hash-consed nodes, homeotic rows, memos keyed by node, data version, type and input binding, level schedule, nothing evicted. The device arena (variant B in phylu) is not built.
- `src/homeotic.rs` — the earlier per-chromosome homeotic tail (fold of a chromosome's shared subtrees into tail slots, encode back to Karva). Its slot-addressed href is superseded by the stable-row-id href of the population design; see its module header.
- `src/wgsl/` — the WGSL kingdom (feature `wgsl`): naga reader cutting a kernel at its effects into a chromosome over `kingdoms/wgsl` tables, scaffold, interpreter, oracle, mutation, rebuild.
- `docs/PLAN_futhark_shapes_product.md` — the shape kingdom's **product** decision: superoptimise shape-polymorphic Futhark kernels (the Souper/STOKE idea, aimed at the GPU — nothing of the kind exists for Futhark). The kernel set is **four** (the draft's nine were cut by a review — five could not be won, one was not even a legal gene — and of the four only A7 can be won); softmax/layernorm/scan need three 1-D vector classes, and only after a measured win. The score is correctness plus a **static cost that is a polynomial in the roles** — traffic, allocations, serial depth — never C-backend wall-clock, which does not transfer to the GPU. Tiling is Futhark's own job (the GPU pipeline's `tileLoops`, and the block+register tiler, which names SGEMM), so the tiler's state is **REPORTED, never filtered on** — the measurement showed the reference is tiled and the winner is not, so a rule that credited only a tiled form would have rejected the only win. Search: GEP for discovery, the e-graph as a **local search on elites** — its rules are equalities by construction, so it moves the cost axis only. **The measured result and the learning curve** are in `docs/measurements/2026-10-27_futhark_shapes_A7.md` and `..._A7_learning.md`; the research write-up is the GECCO mini-poster at `phylu/docs/paper/shape_typed_gecco.tex` (with its PDF beside it) and the **4-page paper** at `phylu/docs/paper/shape_typed_gecco_paper.tex`.
- `docs/index.html` — the **documentation index**: every markdown file in this repository and in the sibling `phylu` checkout, with its title and its first sentence, and a filter box. It is GENERATED by `docs/build_index.py`, whose default is `--check`, and a Rust test (`src/docs_index.rs`) runs that check and walks every link — so a hand-edited index fails `cargo test`, and so does a stale one. Edit the generator, not the page. `docs/REPORT_2026-10-27_shape_kingdom.md` is the one-page progress report on the shape kingdom's state.
- `src/futhark_egraph.rs` — the Futhark kingdom inside Fuller's e-graph: **one egglog sort per kingdom type** (`FR`/`FA`/`FS`/`FF`), so the sort IS the type and the `acc` distinction is structural. The 38 rows map one-for-one onto constructors, plus two e-graph-only ones (`FId`, `FCompose`) whose candidates are compilation-only. Every rule was checked bit-identical against Futhark 0.28.1. See `docs/EGRAPH_futhark.md`.
- `src/futhark_kingdom.rs` + `kingdoms/futhark_true/` — the 1-D Futhark kingdom: 4 types, 38 rows, "shape is a value, not a type". `src/futhark_shapes.rs` + `kingdoms/futhark_shapes/` — the **shape-classed** kingdom: a shape class IS a type (`mat.n.m` = the interface's `[n][m]`), 11 types, 71 rows. The unification happens ONCE, OFFLINE, in `gen_tables.py`, whose 12 witness tests re-check every shape relation from the emitted text — the table is the trust boundary, because the engine no longer checks shapes. The two kingdoms live in separate `Ty` families (`Ty::Futhark` / `Ty::FutharkShape`). `src/futhark_shapes_interp.rs` is the shape kingdom's own interpreter, so the compiled programs and the interpreter can be compared — **bit for bit** on the elementwise paths and **exactly** on the reduction path, with no tolerance anywhere (Futhark's `c` backend reduces with a sequential left fold, measured bit-identical over 600 of 600 elements). Futhark's simplifier folds `x + 0` away, so no row may be spelled as an addition of zero; the `const` rows are spelled `map (\_ -> 0.0)`, a genuine constant, and differ from the identity by VALUE. `src/futhark_shapes_egraph.rs` is its e-graph (one sort per class), whose datatype, ruleset and bridge are GENERATED (`kingdoms/futhark_shapes/egraph.*`) — never hand-written, or they would drift from the table. See `docs/ASSESSMENT_first_class_shapes.md` §15, and the review of the implementation with the disposition of every finding in `docs/reviews/2026-10-26_first_class_shapes_poc_codex.md`. The generator's DEFAULT is `--check`: the committed artefacts are compared byte for byte with what the generator would write, and a Rust test runs that check, so a hand-edited table fails `cargo test`. The **third piece** — shapes that are not the interface's roles — is designed in `docs/ASSESSMENT_dynamic_shapes.md`: the class set's axes may be dynamic and a dimension becomes a value of its own sort, which fits the architecture and costs 3× the gene width (322 → 991 at three roles).
- `src/futhark_shapes_cost.rs` — the shape kingdom's **static cost**: a polynomial in the dimension roles (traffic, allocations, serial depth), generated into `kingdoms/futhark_shapes/costs.tsv` with the generator's own witness test. It is the *filter*, and it is a pre-optimisation model.
- `src/futhark_shapes_gpu.rs` — the **measured** GPU cost: the compiled GPU program (`futhark dev --gpu-mem --compile-imp-gpu`) parsed for its device allocations, its shared memory, its kernels, and whether the block+register tiler fired. This is the cost that *decides*.
- `src/futhark_shapes_evolve.rs` — the search: GEP mutation and crossover for discovery (on a graded agreement measure), the e-graph as a local search on the elites, and the fitness = the reference kernel's value (bit for bit, on a suite of inputs) plus the measured cost. A candidate must also **run on the GPU**: the A7 reference does not — its OpenCL kernel is too big for the device — and the search finds a form that does, with 40 % fewer device allocations. The **SEAM for a GPU-resident population** is here too: `Scorer` (the tables and the layout prepared ONCE, `score`/`score_lenient` over a population of genes, `seed_gene` for the reference), `fitness_of` (the one `f32` the device's selection kernel reads — two bands that cannot overlap, a correct program ranked by `traffic/(traffic+reference)` and an incorrect one by the graded agreement), and `suite`/`input_set` (the deterministic input suite). phylu calls all of it: `phylu::evolve::shape_typed` is the shape kingdom on phylu's typed core — the device draws, varies and selects, the host scores, and the reviews are in `docs/reviews/2026-10-27_shape_typed_phylu_codex_fable.md`.
- `src/parity.rs` + `src/bin/parity.rs` — SymPy-parity scorer, **per-family** (`Family::Algebra|Rational|Trig`).
- `src/python.rs` — PyO3: `denoise`, `denoise_karva`, `physics_mutate`, `physics_mutate_karva`, `master_pset`.
- `parity/` — `gen_corpus.py` (offline sympy→Math corpus), `label_corpus.py` (offline family-labeler for the classifier), `corpus/*.jsonl`.
- `nucleotable/` — subsumed design source of truth (referenced by `geneframe.rs`). `stale/` — delivered briefs, history only.

## Non-obvious things that will bite you

- **Rule families are NON-CONFLUENT.** distribute + trig (or + rational) co-saturated explode the e-graph (verified: pegs CPU, killed runs). The scorer keeps them in separate `Family`s; `denoise` uses only the bounded algebra+powers subset. Do NOT merge all rulesets into one saturation. **Always kill-guard a saturation/parity run** so a divergent rule can't peg the machine: `( cmd & PID=$!; for i in $(seq 1 N); do kill -0 $PID 2>/dev/null||break; sleep 1; done; kill -9 $PID 2>/dev/null )`.
- **distribute must NOT go in `denoise`** — it's a normal-form canonicaliser; `extract_variants` over its unbounded equivalent-class hangs. Scorer-only.
- **egglog does NOT constant-fold f64 literals** unless a rule does it (distribute/rational add the folds).
- **`Protected*` are distinct functions** from raw ops (real-domain raw vs the engine's guarded semantics). Never map a protected geppy name to a raw semantic_id — unsound on negatives/zero.
- **The old "no bare commutativity" advice is nuanced** — egglog's own tests ship bare comm/assoc rewrites; they're fine *bounded*, fatal at unbounded fixpoint with other expand rules. Measured finding: commutativity is NOT the parity wall here (≈2/600 pairs); the gaps are structural.
- **Determinism**: same input + rng_seed = identical output (tests assert). HashMap iteration order bit us once — sort when choosing among equal-keyed entries.
- **The Futhark e-graph's `map id` and its fusion rules used to DIVERGE together.** `map id` puts a class's own `map` node inside that class, and the fusion pattern then matched inside it and built another one: measured 5 → 7 → 13 → 55 → 1357 e-nodes over five iterations, no convergence after six. The **unit laws of composition** (`f . id = f`, `id . g = g`) close the loop — the fused node the pattern mints collapses to one that is already there — so the pair now settles at 6 e-nodes and the two rulesets are **merged** into `FUTHARK_RULESET`. Do not add associativity of `FCompose`: that is the next explosion.
- **Futhark 0.28.1's optimiser does not converge on one legal program** (a reduction over a `acc`, a reversed accumulator-derived operand, and an outer reduction, together). The hang is in the **"Fuse SOACs"** pass, whose fixpoint loop is unbounded (`fuseSOACs Nothing` in `src/Futhark/Passes.hs`); the pass takes a bound and `futhark dev --fuse=N` exposes it. So the program **does** compile, and the engine does it by **capping the compiler's fusion loop**: `futhark_exec`'s bounded-fusion path runs Futhark's own sequential pass list (mirroring `standardPipeline`/`seqPipeline`/`seqmemPipeline`, checked byte-for-byte against `futhark c`) with `--fuse=10`, and the program that hung for ever compiles in **0.12 s** and agrees with the interpreter. This is a **compiler workaround, not an e-graph rescue**: the e-graph's contribution to the outcome is zero, and equality-preserving rewrites of the program do NOT rescue it on their own (measured) — it is the compiler's fusion loop, not the gene. The verdict says so: `Verdict::BoundedFusion`. See `docs/EGRAPH_futhark.md` and `docs/RESCUE_futhark.md`.
- **Futhark 0.28.1's prelude is RANK-1 and has no `matmul`.** `map`/`map2`/`reduce` apply to 1-D arrays of SCALARS; `transpose` is the only 2-D primitive; `zipWith`, `matmul` and `reshape` do not exist. Mapping over a matrix's rows needs an ARRAY-valued function (`map (\row -> …) A`), and `map2` is CURRIED — it needs a TWO-argument function (`[]f32 -> []f32 -> []f32`), which is why the shape kingdom has two function classes. Getting either wrong compiles into a type error, not a wrong answer.
